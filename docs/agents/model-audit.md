# 模型檢查:八類常見錯誤

實體驗證(`npm run verify`)和 `npm test` 都通過的模型照樣會犯這八類錯誤,所以每一類都要用下面的方法另外查。用語照 `CONTEXT.md`。文中舉的圖號例子(前例)是以前的版本犯過的錯,不代表模型現在的狀態。

兩種用法:

- **複查**:範圍是第 86 種以後,每張圖做步驟 1–5,只記錄、不修改模型,修正另開票。
- **改動或新增模型**:做步驟 1–4,查到的問題當場修,不寫逐圖表格。

寫了「決定(日期)」的段落是**定案**,出現在 `.scratch/physical-verification/pending.md` 與 `.scratch/model-audit/` 各族檔的「需要你決定的」裡:發現和定案衝突時,寫成「推翻建議」,附上理由,交給維護者決定——複查寫進族檔的「需要你決定的」;改動時那一處照定案維持,推翻建議寫在回報裡。

## 每張圖的步驟

1. **讀原文與插圖**:`node tools/audit.mjs 圖號` 印出原文與各零件的動作摘要;看 `images/圖號.png`。把原文裡每一句可以驗證的敘述列出來(誰帶動誰、轉向、幾圈對幾程、順序、狀態切換時發生什麼)。
2. **讀定義**:`models/figNNN.js` 與它 import 的共用模組;測試在 `tests/` 裡搜尋圖號。
3. **看動作**:經截圖服務截 `tools/model-strip.html?fig=N&vs=…`(用法見 `tools/shot.mjs` 檔頭),輸出寫到 `.playwright-mcp/model-audit/`(不進 git),檔名以圖號開頭。一頁放齊這個狀態要看的相位,至少四個(一圈或一個往復平均取點,再加上原文提到的關鍵時刻);每個狀態一頁(`state=`),斜後方(`dir=`)與放大接觸處(`fit=`)各一頁。一頁可能切成好幾張輸出,每張都看。
4. **逐類檢查**:下面八類逐類查。
5. **記錄**(複查):寫進這次掃描的逐圖表格(見最後一節)。

這張圖的完成條件:

- 複查:八類每一類都是「通過」(附上看了什麼)、「問題」(附上證據)或「不適用」(附上理由),沒有空格。
- 改動或新增:回報裡八類每一類都寫出看了什麼(或不適用的理由),查到的問題都修好,`npm run verify -- 圖號` 與 `npm test` 通過。

## 八類

### 1. 原文:斷言照原文,不照模型

模型、測試與複查表上的「通過」都可能只是在重複模型自己的行為。逐句拿步驟 1 列出的敘述對照模型實際的動作,數字也要對:第 175 種的原文是「活塞每一程曲柄轉一圈」,模型做成一圈往返一次,測試把錯誤的行為鎖住了,複查表也記成「通過」。

- 測試裡的斷言要能對到原文的某一句;對不到原文、只描述模型輸出的斷言,記成問題。
- 有狀態(前進 / 後退、接上 / 脫開)的圖,狀態要演出原文說的原理。第 179 種「後退」時軸照樣往同一個方向轉,換向的原理就沒有演出來。

### 2. 權宜:為了閃開干涉而改壞結構

為了讓驗證通過、零件不互相穿透而做的幾何調整,常常做出實物上更不成立的東西。找出每一處這種調整,問一句:真的機器是不是這樣做的?

找的地方:

- 註解裡的「為了…不碰」「做小」「開口」「只到…背面」「縮短」「偏離插圖」。
- 連桿的 `stretch: true`(`grep -n "stretch: true" models/`)。
- 軸只伸到一半、零件被切開讓別的零件穿過。

前例:第 176/177 種把眼的兩側切開、環做小,讓手腕銷穿出去,結果環斷成兩塊;第 171、185 種的軸只伸到偏心輪背面,真正的做法是偏心環套在偏心輪外面、軸整根穿過;第 175 種的連桿會伸縮。正確的修法是照真的機器重新安排(把溝槽只開半個厚度、改成偏心環、改比例),不是截短或切開。

### 3. 盲點:實體驗證看不到的三件事

實體驗證只查零件「之間」的干涉,以及會動的零件有沒有連回主動件。下面三件要自己查:

- **一件**:同一個零件的每一塊(本體與所有 `pieces`)都要和別塊相連。
  - 跑 `node tools/one-piece.mjs [圖號或範圍…]`,報出的每一項都要找出實物上的理由,否則記成問題;銷在同一零件的孔裡留了間隙也會報。
  - 工具看不到兩種,要自己查:板件的輪廓被溝槽或開口切成互不相連的幾塊(同一塊之內),以及另列成零件、應該裝在別的零件上的塊(第 235 種的擋銷)。
  - 前例:第 176/177 種的環被貫穿的溝槽切成兩塊,眼的上半段懸空;第 179 種的半圓凸出部分和偏心輪正面之間有空隙;第 146 種的軛不是一件。
- **剛性**:跑 `node tools/rigid-links.mjs [圖號或範圍…]`,它會列出兩端距離會變的桿(from/to 擺的零件,與 kind 為 `rod` 的路徑零件——折線任一段變長就報)。每一根都要找出實物上的理由(桿在長槽或導套裡滑、伸縮軸),而且那個長槽或導套要畫出來;找不到理由的,記成問題。帶 `stretch: true` 的桿記在第 2 類。
- **真的碰到**:註解或原文說「推」「頂」「撥」「靠在」「帶動」的每一對零件,在接觸的姿勢下兩者要在同一個深度範圍內,而且平面上的間隙接近 0。只要套在軸上,實體驗證就算「連回主動件」,不管凸出部分有沒有碰到:第 179 種軸上的凸出部分在半圓凸出部分的內側,從來碰不到;第 147 種的滾子沒有靠在斜面上;第 144 種的支點只是一塊板,沒有樞銷。

### 4. 驅動:動力來源與被調節的對象

讀者要看得出機構為什麼動、在調什麼。調速、調節、計量、汲水這類模型,要補出驅動來源(水流、引擎的軸)與被調節的對象(閘門、閥門);補上的零件在註解裡標明是推斷。補上的驅動也要真的會動:第 147 種補的斜齒輪不會轉,維護者就問「這是做什麼的」。前例:第 162、163 種補上水車、水道與閘門。

### 5. 記號:插圖上的記號要判讀對

- 虛線的軌跡或圓是「預覽運動線」,不是零件(第 168、169 種畫成了零件)。
- 虛線畫的零件是藏在後面的零件(第 146 種的溝在圓盤後面)。
- 斜線剖面是剖開的斷面,箭頭是運動方向(查轉向和模型一致)。

### 6. 全程:動作的幅度與中途的接觸

只看初始畫面會漏掉動作中途的錯。在步驟 3 的每一個相位上,確認:

- 幅度走滿:銷走完整條溝(第 98 種)、剪具會閉合(第 130 種)、繩捲在鼓上(第 129 種)、繩跟著輪緣走(第 134 種)。
- 中途的接觸位置對:爪的形狀咬得到齒(第 116 種)、偏心桿端的銷對著連桿上的孔。
- 正面被擋住的地方,從斜後方看:第 179 種的凸出部分被軸的前端遮住。
- 虛擬主動件(轉速、水量)的滑桿從頭到尾都有看得出的變化。公式照真實物理算、但滑桿有一大段沒有反應,也記成問題,讀者會當成壞掉(第 161、170 種的圓錐擺)。

### 7. 讀得出:讀者看得出狀態與轉向

- 轉向箭頭沒有被零件擋住(第 115 種)。
- 狀態切換時看得出差別(第 110 種的半螺帽)。
- 跟著主動件一起轉的零件同色,是主動件的抓取處(第 143 種的蝸桿)。
- 機構最終帶動的零件標了目標件(`target`)。

### 8. 橫向:同類的圖一起查

每查到一個問題,就查同類的圖。複查時把它們列在那一筆問題裡;改動時同樣的錯當場一起修,修不了的開票:

- import 同一個共用模組的圖:`grep -ln "from \"./模組名.js\"" models/`。
- 同一種機構的其他圖:同一族、或原文提到「如同第 N 種」的圖。

前例:第 171 種改成偏心環時沒有去查同樣用 `link-motion.js` 的第 185 種;第 161、170 種的調速器修好之後,同類的第 147 種又被退回一次。

## 記錄的格式

一族一個檔:`.scratch/model-audit/NN-slug.md`,族的分法與編號照 `.scratch/recheck-86-507/tables/README.md`。檔案依序分四段:

1. **基準**:掃描前對整個範圍跑 `npm run verify -- 範圍`、`node tools/one-piece.mjs 範圍`、`node tools/rigid-links.mjs 範圍`,寫下結果(未豁免的問題與豁免各幾項、兩個工具報出幾項)。
2. **需要你決定的**:推翻建議,以及修法有不只一種、要維護者選的問題。每一題列出選項,各附代價,標出建議的那一個;維護者決定後在題下寫「決定(日期)」。
3. **逐圖表格**:每張圖一列,欄位是圖號與八類;格子裡寫「通過:看了什麼」「問題:見 #編號」或「不適用:理由」。
4. **問題清單**:每一筆有編號、圖號、類別(1–8)、證據(截圖的檔名、數字、原文的句子)、建議的修法、同類要一起查的圖(第 8 類)、是否和維護者的定案衝突。

整族的完成條件:基準寫了三個工具的結果;範圍內每張圖都有一列、每一列八格都填了;每一筆問題都有證據與第 8 類的結果;和定案衝突的每一筆在「需要你決定的」都有一題。
