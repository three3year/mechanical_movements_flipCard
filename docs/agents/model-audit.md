# 模型檢查:八類常見錯誤

這八類是 2026-10-07 全書複查之後,維護者看網頁仍然退回的錯誤。實體驗證(`npm run verify`)和 `npm test` 都通過的模型照樣會犯,所以每一類都要用下面的方法另外查。用語照 `CONTEXT.md`。

掃描時只記錄、不修改模型;修正另開票。維護者已經決定過的事(`.scratch/physical-verification/pending.md` 的「需要你決定的」各段裡寫了「決定(日期)」的,以及各族逐圖表格裡「維護者決定」的)是定案:發現和定案衝突時,寫成「推翻建議」,附上理由。

## 每張圖的步驟

1. **讀原文與插圖**:`node tools/audit.mjs 圖號` 印出原文與各零件的動作摘要;看 `images/圖號.png`。把原文裡每一句可以驗證的敘述列出來(誰帶動誰、轉向、幾圈對幾程、順序、狀態切換時發生什麼)。
2. **讀定義**:`models/figNNN.js` 與它 import 的共用模組;測試在 `tests/` 裡搜尋圖號。
3. **看動作**:用不快取或任何靜態伺服器開 `tools/model-strip.html?fig=N&vs=…`,至少截四個相位(一圈或一個往復平均取點,再加上原文提到的關鍵時刻),每個狀態都截;再用 `dir=` 從斜後方截一張,用 `fit=` 放大接觸處。Playwright 不能用時,用 headless Chrome:`chrome --headless=new --use-angle=swiftshader --enable-unsafe-swiftshader --window-size=W,H --virtual-time-budget=15000 --screenshot=out.png URL`(一次大約只來得及畫兩個相位,分幾次截)。
4. **逐類檢查**:下面八類都查,每一類都要有結論。
5. **記錄**:寫進這次掃描的逐圖表格(見最後一節)。

這張圖的完成條件:八類每一類都是「通過」(附上看了什麼)、「問題」(附上證據)或「不適用」(附上理由),沒有空格。

## 八類

### 1. 原文:斷言照原文,不照模型

模型、測試與複查表上的「通過」都可能只是在重複模型自己的行為。逐句拿步驟 1 列出的敘述對照模型實際的動作,數字也要對:第 175 種的原文是「活塞每一程曲柄轉一圈」,模型做成一圈往返一次,測試把錯誤的行為鎖住了,複查表也記成「通過」。

- 測試裡的斷言要能對到原文的某一句;對不到原文、只描述模型輸出的斷言,記成問題。
- 有狀態(前進 / 後退、接上 / 脫開)的圖,狀態要演出原文說的原理。第 179 種「後退」時軸照樣往同一個方向轉,換向的原理就沒有演出來。
- 公式照真實物理算,但滑桿有一大段沒有反應(第 161、170 種的圓錐擺),也記成問題:讀者會當成壞掉。

### 2. 權宜:為了閃開干涉而改壞結構

為了讓驗證通過、零件不互相穿透而做的幾何調整,常常做出實物上更不成立的東西。找出每一處這種調整,問一句:真的機器是不是這樣做的?

找的地方:

- 註解裡的「為了…不碰」「做小」「開口」「只到…背面」「縮短」「偏離插圖」,以及 pending.md 的「為了實物可行而偏離插圖之處」。
- 連桿的 `stretch: true`(`grep -n "stretch: true" models/`)。
- 軸只伸到一半、零件被切開讓別的零件穿過。

前例:第 176/177 種把眼的兩側切開、環做小,讓手腕銷穿出去,結果環斷成兩塊;第 171、185 種的軸只伸到偏心輪背面,真正的做法是偏心環套在偏心輪外面、軸整根穿過;第 175 種的連桿會伸縮。正確的修法是照真的機器重新安排(把溝槽只開半個厚度、改成偏心環、改比例),不是截短或切開。

### 3. 盲點:實體驗證看不到的三件事

實體驗證只查零件「之間」的干涉,以及會動的零件有沒有連回主動件。下面三件要自己查:

- **一件**:同一個零件(一個 `group` 的所有 `pieces`)的每一塊都要和別塊相連。逐塊比對位置與深度範圍(`at` 的 z ± 厚度 / 2),找出懸空的塊;再看板件的輪廓有沒有被溝槽或開口切成互不相連的幾塊。前例:第 176/177 種的環被貫穿的溝槽切成兩塊,眼的上半段懸空;第 179 種的半圓凸出部分和偏心輪正面之間有空隙;第 146 種的軛不是一件。
- **剛性**:跑 `node tools/rigid-links.mjs`,它會列出兩端距離會變的桿。每一根都要找出實物上的理由(桿在長槽或導套裡滑、伸縮軸),而且那個長槽或導套要畫出來;找不到理由的,記成問題。彈簧不在清單裡。
- **真的碰到**:註解或原文說「推」「頂」「撥」「靠在」「帶動」的每一對零件,在接觸的姿勢下兩者要在同一個深度範圍內,而且平面上的間隙接近 0。只要套在軸上,實體驗證就算「連回主動件」,不管凸出部分有沒有碰到:第 179 種軸上的凸出部分在半圓凸出部分的內側,從來碰不到;第 147 種的滾子沒有靠在斜面上;第 144 種的支點只是一塊板,沒有樞銷。

### 4. 外在:驅動來源與被調節的對象

讀者要看得出機構為什麼動、在調什麼。調速、調節、計量、汲水這類模型,要補出驅動來源(水流、引擎的軸)與被調節的對象(閘門、閥門);補上的零件在註解裡標明是推斷。補上的驅動也要真的會動:第 147 種補的斜齒輪不會轉,維護者就問「這是做什麼的」。前例:第 162、163 種補上水車、水道與閘門。

### 5. 記號:插圖上的記號要判讀對

- 虛線的軌跡或圓是「預覽運動線」,不是零件(第 168、169 種畫成了零件)。
- 虛線畫的零件是藏在後面的零件(第 146 種的溝在圓盤後面)。
- 斜線剖面是剖開的斷面,箭頭是運動方向(查轉向和模型一致)。

### 6. 全程:動作的幅度與中途的接觸

只看初始畫面會漏掉動作中途的錯。在步驟 3 的每一個相位上,確認:

- 幅度走滿:銷走完整條溝(第 98 種)、剪具會閉合(第 130 種)、繩捲在鼓上(第 129 種)、繩跟著輪緣走(第 134 種)。
- 中途的接觸位置對:爪的形狀咬得到齒(第 116 種)、偏心桿端的銷對著連桿上的孔。
- 正面被擋住的地方,從斜後方看:第 179 種的凸出部分被軸的前端遮住。
- 虛擬主動件(轉速、水量)的滑桿從頭到尾都有看得出的變化。

### 7. 讀得出:讀者看得出狀態與轉向

- 轉向箭頭沒有被零件擋住(第 115 種)。
- 狀態切換時看得出差別(第 110 種的半螺帽)。
- 跟著主動件一起轉的零件同色,是主動件的抓取處(第 143 種的蝸桿)。
- 機構最終帶動的零件標了目標件(`target`)。

### 8. 橫向:同類的圖一起查

每記下一個問題,就查同類的圖,把它們列在那一筆問題裡:

- import 同一個共用模組的圖:`grep -ln "from \"./模組名.js\"" models/`。
- 同一種機構的其他圖:同一族、或原文提到「如同第 N 種」的圖。

前例:第 171 種改成偏心環時沒有去查同樣用 `link-motion.js` 的第 185 種;第 161、170 種的調速器修好之後,同類的第 147 種又被退回一次。

## 記錄的格式

一族一個檔:`.scratch/model-audit/NN-slug.md`,族的分法與編號照 `.scratch/recheck-86-507/tables/README.md`(第 1–85 種另分族,同樣的格式)。檔案分兩段:

1. **逐圖表格**:每張圖一列,欄位是圖號與八類;格子裡寫「通過:看了什麼」「問題:見 #編號」或「不適用:理由」。
2. **問題清單**:每一筆有編號、圖號、類別(1–8)、證據(截圖的檔名、數字、原文的句子)、建議的修法、同類要一起查的圖(第 8 類)、是否和維護者的定案衝突。

整族的完成條件:範圍內每張圖都有一列、每一列八格都填了,而且每一筆問題都有證據與第 8 類的結果。
