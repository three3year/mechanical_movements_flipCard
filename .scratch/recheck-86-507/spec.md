# 第 86–507 種複查:套用回饋規則、原文對照、動力重演與插圖對照

Status: ready-for-agent

**來源:** 2026-10-07 與維護者的 grilling。維護者看過第 35–85 種後退回了十幾張(第 35、47、48、63、65、73、76、77、80、83 種等),要把這些回饋套用到第 86 種以後的全部模型。

## Problem Statement

全書 507 張模型都已通過實體驗證(干涉、憑空連動),但維護者逐張看第 35–85 種時,還是退回了十幾張。退回的原因,實體驗證都查不到:

- **演出的動作**:棘爪、鉤、撥爪的位置照主動件的進度表給出,和推它的零件只是時間上剛好對上,外形並沒有真的相碰(第 63、65、73、76、77、80、83 種)。
- **看不出在轉**:軸和對稱的輪轉起來看不出轉向(第 47、48 種)。
- **看不到相連**:零件跟著動,卻看不出是裝在什麼上面(第 67、76 種)。
- **落下沒有過程**:靠重力落下的零件瞬移到底(第 64、66、67 種)。
- **主動件、目標件、動作順序不對**:例如第 35 種的輸入選錯、第 63 種先後順序和原文相反。

第 86 種以後的 422 張是用同樣的方法做出來的,很可能有同樣的問題,只是維護者還沒看到。另外有 42 張動力重演不成立、先以「未修」豁免帶過,其中 21 張在擒縱機構章;還有 9 張在重演名單上卻沒有宣告。維護者不想再一張張看、一張張退回。

## Solution

實作者照章節順序,把第 86–507 種逐族複查一遍。每一族查完就把該族的問題修掉,接著做下一族,不必等維護者看過。

每張圖都查四項:

1. **回饋規則**(見下方「回饋規則」)。
2. **原文對照**:轉向、轉速比、動作順序。
3. **動力重演**:靠接觸或重力運作的機構要宣告重演並通過。
4. **插圖外形對照**:模型和插圖並排截圖,認得出是同一個機構。

遇到要判斷的地方,實作者照「原文 > 實物可行 > 插圖外形」自己決定,寫進模型註解與待確認清單。維護者以前做過的決定也重查,但只提建議、不改。每族留一張逐圖表格,沒問題的圖也有一列,維護者事後看得出哪張查過、查了什麼。

### 回饋規則

1. 靠接觸運作的從動件**由接觸算**:被推多遠、何時滑脫、停在哪裡,都由兩者外形相碰決定,不能是**演出的動作**。
2. 靠重力或彈簧落下、彈回的零件,演出加速的過程,到底撞停,不能瞬移。
3. 零件看得到裝在什麼上面:軸、銷、轂、輻條、機架、支座。原圖沒畫、屬於推斷的,寫進模型註解。原圖沒畫的整組傳動也要補,不能以「簡化」帶過。
4. 會轉的零件(包括軸)看得出轉向:一處記號色加轉向箭頭,停住時箭頭隱藏;軸用鍵條當記號。並排同向的輪只留一個箭頭,半透明的輪不顯示箭頭。
5. 皮帶、繩、鍊條分成實色的色段,用黑色記號隔開,色段跟著材料走,不用綠色。
6. 目標件照「這組結構存在的目的」逐張重判。擒縱各圖與第 102、145、158 種等,以前改標在運動鏈另一端的,也要重判。
7. 主動件:原文有寫輸入就照原文;沒寫時,取等速轉、軸固定在機架上的那一個(見用語表「主動件」)。
8. 從動件只在真的被帶動時才動,動作的先後照原文。
9. 原文描述的效果(交替、自動反向、到終點就換向等),播放時自己呈現,不靠讀者按狀態按鈕;只有原機構由操作的人切換的(手扳離合桿等)才用按鈕。
10. 棘輪與擒縱這一族:棘爪、鉤、掣子做成鉸接的自由零件,靠自重或彈簧搭在齒上。棘輪齒用鋸齒形(推的一面陡、背面斜),每程的推進量由接觸算。

## User Stories

### 讀者

1. 身為讀者,我想看到棘爪真的推著齒走、鉤真的從齒下把輪提起,這樣我學到的是實物會怎麼動。
2. 身為讀者,我想看到從動件在主動件碰到它之前不動、滑脫之後才落下,這樣我看得出因果。
3. 身為讀者,我想看到落下的錘、擺錘、棘爪是加速掉下去的,這樣它看起來是重力造成的,不是瞬間跳過去。
4. 身為讀者,我想看到每個會動的零件裝在軸、銷或機架上,這樣我知道是什麼撐著它、什麼帶動它。
5. 身為讀者,我想看得出每根軸、每個輪往哪個方向轉,即使它是整圈對稱的,這樣我能對照原文說的轉向。
6. 身為讀者,我想看得出皮帶、繩、鍊條在移動、往哪移動,這樣我知道動力怎麼傳過去。
7. 身為讀者,我想一眼分出橘色的主動件與藍綠色的目標件,這樣我知道輸入在哪、這組機構最後要帶動什麼。
8. 身為讀者,我想主動件是原文說的那個輸入;原文沒說時,是等速轉、軸固定在機架上的那個,這樣主動件符合機構的常理。
9. 身為讀者,我想看擒縱機構時,藍綠色標在這組結構存在的目的上,這樣我理解擒縱在控制什麼。
10. 身為讀者,我想模型的轉向、轉速比和原文一致,這樣我讀原文時對得上。
11. 身為讀者,我想模型的動作先後和原文寫的順序一致,這樣我能照著原文一步步看。
12. 身為讀者,我想按播放就看到原文說的交替、自動反向,不必自己去找狀態按鈕,這樣我不會錯過機構的重點。
13. 身為讀者,我想原機構由人手切換的地方(離合桿、換向桿)仍能用按鈕切換,這樣我能自己試。
14. 身為讀者,我想模型和插圖並排時認得出是同一個機構,這樣我切換插圖與模型時不會迷路。
15. 身為讀者,我想零件不互相穿過、該碰的地方真的貼著,這樣模型看起來是實物做得出來的。

### 維護者

16. 身為維護者,我想每一族結束時有一張逐圖表格,每張圖一列、每個檢查項目一欄,這樣我分得出「查過沒問題」和「漏查」。
17. 身為維護者,我想表格裡寫出每張圖修了什麼、為了什麼偏離插圖或原文,這樣我不用讀程式碼也知道改了哪裡。
18. 身為維護者,我想實作者拿不準的地方先照「原文 > 實物可行 > 插圖外形」做決定,記進待確認清單,這樣進度不會卡在等我回覆。
19. 身為維護者,我想我以前做過的決定(第 87、186、187 種先維持現狀、第 462 種維持現狀、第 504 種用俯視圖、第 384、504 種不放大取景、14 張只有主動件在動而不標目標件等)被重查,但只寫成建議、不被直接推翻,這樣我的決定不會被默默改掉。
20. 身為維護者,我想推翻舊決定的建議列在待確認清單最上方,這樣我一打開就看到。
21. 身為維護者,我想動力重演不成立的 42 張都改成由接觸算、重演通過,這樣「未修」豁免消失。
22. 身為維護者,我想真的卡在重演引擎的限制時,可以寫一個有具體原因的豁免,而不是用「未修」帶過,這樣豁免清單上的每一項都說得出為什麼可以接受。
23. 身為維護者,我想重演名單上還沒宣告的 9 張(第 181–184、294、295、300、301、470 種)都補上宣告,或寫明為什麼不適用,這樣名單上沒有漏網的。
24. 身為維護者,我想用腳本產生、剛好通過的那幾張重演(第 114、173、213、233、234、251、288、292、402 種)逐張確認通過的理由,這樣「通過」不是碰巧。
25. 身為維護者,我想第 86 種以後還在的「演出的接觸」豁免(17 張)都改成由接觸算,或改寫成具體原因,這樣這類豁免不會繼續累積。
26. 身為維護者,我想修共用模組(齒形、棘輪、接觸)時第 1–85 種照樣通過測試與實體驗證,這樣前面修好的不會又壞掉。
27. 身為維護者,我剛看過的第 35–85 種若因共用模組改動而外觀有變,我想在表格裡特別看到,這樣我知道要回頭再看哪幾張。
28. 身為維護者,我想每一族結束都有一個提交,說明這一族改了什麼,這樣我能逐族看改動、需要時逐族退回。
29. 身為維護者,我想每一族的測試斷言對應原文(轉向、比例、順序、每程推進量),這樣以後改模型時,偏離原文會被測試抓到。
30. 身為維護者,我想這份工作能分成多個 session 照章節做下去,每個 session 從上次停的地方接著做,這樣不會因為對話太長而品質下降。
31. 身為維護者,我想待確認清單在每一族結束時更新,這樣我隨時打開都看到最新狀態。
32. 身為維護者,我想主動件因規則 7 換人的圖都在表格裡標出來,這樣我知道哪些模型的橘色換了零件。
33. 身為維護者,我想目標件重判後換了零件的圖都在表格裡標出來,這樣我能逐張確認。
34. 身為維護者,我想原文和插圖衝突、照原文做而偏離插圖的地方都寫進模型註解,這樣以後的人不會把它改回插圖的樣子。

## Implementation Decisions

- **順序與分批**:照圖號順序,以章節為一族,18 族:曲柄與凸輪(86–101)、螺旋機構(102–112)、齒條與小齒輪(113–127)、運動轉換與應用(128–154)、引擎與調速機構(155–190)、變速與曼格機構(191–224)、棘輪與擒縱(225–242)、接頭與器具(243–287)、擒縱機構(288–314)、擺與鐘錶調節(315–321)、平行運動與引擎(322–349)、雜項裝置(350–402)、繪圖儀器(403–411)、雜項與旋轉引擎(412–429)、水車與泵(430–469)、蒸汽與氣體裝置(470–483)、風力、船舶與起重(484–494)、儀錶與周轉輪系(495–507)。超過一個 session 能做完的大章(例如雜項裝置 53 張、接頭與器具 45 張)可以再切成幾段,但一段結束時那一段的表格、提交與清單都要完成。
- **一族的流程**:查完整族、記下問題 → 修掉 → 跑測試、實體驗證、截圖確認 → 寫逐圖表格 → 更新待確認清單與豁免清單 → 提交 → 做下一族。不等維護者看過。
- **判斷的優先序**:沿用用語表「實體驗證」的「原文 > 實物可行 > 插圖外形」。決定寫進模型註解;偏離插圖或原文、或拿不準的,另外寫進待確認清單。
- **舊決定**:全部重查。認為該推翻的,只在待確認清單最上方寫建議,不改模型;同一張圖的其他問題照修。
- **動力重演的完成標準**:每張靠接觸或重力運作的模型都要宣告並通過。真的卡在重演引擎的限制時(例如原書沒有彈簧力、摩擦的資料,預設值下做不出來),寫一個說得出具體原因的豁免;原因不能以「未修:」開頭。腳本產生、通過的宣告,逐張確認通過的理由。
- **「演出的接觸」豁免**:能改成由接觸算的就改,改不了的改寫成具體原因。
- **共用模組可以改**:前提是第 1–85 種的測試與實體驗證照樣通過;第 35–85 種若外觀有變,在該族的表格另列出來。
- **逐圖表格**:每族一張,寫在這個功能的資料夾裡(一族一個檔或集中一份皆可,以維護者好找為準)。每張圖一列,欄位是四個檢查項目(回饋規則、原文、動力重演、插圖),外加「改了什麼 / 偏離了什麼」。沒問題的寫「通過」,有修的寫修了什麼;主動件換人、目標件換人、第 35–85 種外觀受影響,要明確寫出。
- **待確認清單**:沿用實體驗證的那份清單(它是審核關卡,改它時照審核關卡的鏡像流程重新發布)。新增「推翻舊決定的建議」一節放在最上方。
- **用語**:用語表已新增「由接觸算」「演出的動作」,並在「主動件」補上原文沒指明輸入時的選法。表格、註解、提交訊息一律用這些詞。
- **不新增檢查工具**:證明一張圖查過、修好,只用現有的三個檢查點(見 Testing Decisions);瞬移用現有的掃描工具查。
- 模型本身仍依幾何關係連動,不用物理引擎(ADR-0001);物理引擎只用在實體驗證(ADR-0003)。流體仍是示意(ADR-0002)。

## Testing Decisions

- **三個檢查點,都是現有的**:
  1. **模型定義的測試**(`npm test`):從外部看 `pose()` 的輸出,斷言對應原文——轉向、轉速比、動作順序、每程推進量、接觸處不穿入、從動件在被碰到之前不動。不測內部的函式或中間值。前例:第 63、65、73、76、77、80、83 種在間歇運動測試檔裡的斷言(每程前進量、接觸不穿入),第 35 種在齒輪測試檔裡的主動件 / 目標件斷言。
  2. **實體驗證**(`npm run verify`,可只跑該族的圖號):干涉、憑空連動、動力重演都要通過,不能留過時的豁免。動力重演通過,是判斷「由接觸算」的主要依據。
  3. **插圖對照截圖**:用模型預覽頁把插圖與模型並排,取幾個相位,看外形、轉向記號、相連處、目標件顏色。結果寫進逐圖表格。
- 瞬移用現有的掃描工具查;一族修完後在該族圖號上沒有報出(刻意的除外,寫進表格)。
- 修了共用模組時,`npm test` 與全書 `npm run verify` 都要跑,不只跑該族。
- 新的斷言放進該章現有的測試檔,一章一檔的慣例不變。斷言要能指回原文的某一句(測試的說明或註解引原文)。

## Out of Scope

- 第 1–85 種的複查(維護者已經看過)。共用模組改動造成的連帶影響要處理,但不主動複查這些圖。
- 新增全書規則門檻或新的檢查工具(例如自動檢查每個轉動零件都有記號);這次只用現有的三個檢查點。
- 推翻維護者的舊決定(只寫建議)。
- 改變模型的呈現方式或讀者介面(取景策略、按鈕、頁面版面);規則 9 只是讓既有的播放呈現原文的效果。
- 讓模型本身改用物理引擎。
- 重演比快慢(原書沒有重量與彈簧力的資料)。
